# Wedded App: Project Brief

A complete picture of the app for someone planning features without access to the code. Written 2026-10-06 from the `main` branch on GitHub (`faizant316/wedding-vendor-app`), plus the open pull requests, which are marked as such. The source of truth inside the repo is `docs/PRODUCT_VISION.md` (about 150 KB), `docs/DECISIONS.md`, `docs/PROJECT_PLAN.md` and `docs/RESEARCH_GROWTH.md`.

## 1. What the app is and who it's for

**Wedded App** is a phone app where South Asian and Middle Eastern families in Northern California plan a wedding and find the vendors for it. It starts with Punjabi Sikh weddings (the default) and also covers Punjabi Hindu, Pakistani, Muslim and Arab weddings. A family picks its traditions and events (Roka, Mehndi, Jaago, Anand Karaj, Nikah, Walima, Reception…). The app shows which vendor types each event needs: halls, gurdwaras, caterers, dhol players, photographers, mehndi artists and so on. It lists local vendors near the family's city, lets the family save them per event and ask for a price and date, and helps them track what's booked with a countdown to the day. Families plan together: one wedding plan is shared with relatives through invite links. Vendors get free listings, menus, a calendar, chat with families and monthly stats. The users include elders who aren't comfortable with technology, so the app uses large text, plain warm language, English and Punjabi (Gurmukhi) throughout, and no multi-step flow without visible progress. Two co-founders, Kirat (Gurkirat Bagri) and Fezy, build it with Claude Code. The next milestone is a **November 2026 demo** with one real banquet hall (vision §13).

## 5. Visual design

- **Overall:** Apple's **iOS 26 system design**, so it feels native to an iPhone: a grouped grey page, white inset-grouped rows and cards with large radii, large titles that collapse into a glass nav bar when scrolling, capsule buttons, a floating Liquid Glass tab bar, SF Symbols, spring animations and haptics. **One tint colour, maroon**, the way an Apple app has one accent. Glass is only for floating chrome (tab bar, bars over photos, sheet buttons), never for content. #114 lets Home's tiles and cards also use saffron and rose fills.
- **Light palette:** page `#F2F2F7`, surface `#FFFFFF`, text `#000000`, secondary text `#6C6C70` (the high-contrast iOS grey, 5.1:1, because elders find Apple's default too faint), separator `#C6C6C8`, **primary maroon `#8A1C30`** (9.2:1), primary tint `#F5E8EB`, marigold accent `#F0A030` (fills only), saffron text `#A8500A` (founding badges), rose `#B4335C`, success `#248A3D`, error `#D70015`. The countdown card is a maroon-to-rose gradient (`#8A1C30` → `#B4335C`) with white text. The welcome and first questions use a plain white "canvas" with grey cards.
- **Dark palette:** true black page, surfaces `#1C1C1E` / `#2C2C2E`, text white, secondary `#A1A1A6`, and **primary becomes a lighter rose `#F2718A`** for text and icons, with `#B8354E` for filled buttons. Every key exists in both palettes; Settings → Appearance picks Automatic, Light or Dark.
- **Type:** San Francisco (system) on iPhone, Inter elsewhere; **Mukta Mahee** for Gurmukhi, drawn 8% larger with taller line heights. The scale mirrors iOS Dynamic Type: display 34, title 28, section 22, heading 20, body large 19, **body 17**, label 15, button 17 semibold, caption 13. An in-app Text size setting multiplies everything (each style has a maximum). The welcome PRs bring in serif display faces (Fraunces in #115, Playfair Display in #105).
- **Sizes and spacing:** spacing 4 / 8 / 12 / 16 / 24 / 32 / 48; radius 26 for cards, 18 for photos, 14 for fields, 38 for sheets, capsules for buttons and chips; **nothing tappable is under 48 pt**; buttons and fields are 52 tall; list rows 60; the page gutter is 16; the floating tab bar is 64 tall, inset 16 from the edges.
- **Logo:** the **ribbon knot**: a black satin ribbon with engraved shading, tied into a W shape. It is the app icon (black on white) and the intro animation. White version for dark mode. The knot's loose end was closed on 2026-10-06; that fix is on the intro branch.
- **Accessibility:** contrast ratios are computed for every text colour; Reduce Motion is respected everywhere (Reanimated skips layout animations, the intro just fades); at very large text sizes layouts stack (for example the Save / Ask bar and the bento grid).
- **Components:** custom, no UI kit. They live in `src/components` and read colours through `useColors()` / `makeStyles()`. On a computer's browser, `WebFrame` shows the app inside an iPhone-sized frame.

## 6. Data models

All tables are in Postgres (`public` schema) with row-level security. Names that show in the app are `jsonb {en, pa}` or have `_pa` columns. Rules-heavy writes go through SQL functions, never straight table writes.

**Reference data** (read-only for everyone; defined in migrations so every environment gets it):

- `cultures`: slug, name, script (gurmukhi / shahmukhi / devanagari / arabic / latin), is_default, shows_auspicious_dates, `background_slug`, `faith_slug`, sort_order. Five rows: punjabi-sikh (default), punjabi-hindu, pakistani, muslim, arab.
- `backgrounds` (Punjab, Pakistan, India, Middle East, Afghanistan, Bangladesh) and `faiths` (Sikh, Hindu, Muslim, Christian): slug, name.
- `events`: slug, name, aliases, host_side, timing, typical_guests_min / max, summary.
- `culture_events`: culture, event, phase (before / day / after), sort_order, `local_name` (what this tradition calls a shared event, e.g. Mayun, Henna night), `is_core` (main event).
- `category_groups` (Venues, Food, Music…) and `categories` (vendor types): slug, group, name, aliases, is_religious, serves_alcohol.
- `event_categories`: event, category, importance (essential / nice to have).
- `cities` (101 NorCal cities with points and nicknames), `area_codes` (9 chips: centre city and radius), `zip_codes` (California).
- `app_config`: key / value (for example the app-wide daily email cap).

**Vendors:**

- `vendors`: id, slug, status (published…), is_sample, name / name_pa, tagline(_pa), bio(_pa), city, `location` (PostGIS point), address_visibility, address_line, service_radius_miles, will_travel, call / text / whatsapp phones, instagram_handle, website_url, preferred_contact, office_hours, languages, price_display / price_from / price_to / price_unit / price_note, years_in_business, team_size, **founding_number**, details (jsonb hall facts: seats, alcohol, outside caterers, ghori, curfew, parking…), calendar_updated_at.
- `vendor_private`: email, checks_email, street address, exact location, owner name, notes. **The API can never read it.**
- `vendor_categories` (up to 3 per vendor, position 1 is the main one), `vendor_events`.
- `vendor_media`: storage_path (files at `{400,1080,1600}.webp`), width, height, blurhash, is_cover, sort_order, event, venue (where it was taken), credit vendor or text. Public bucket `vendor-media`.
- `vendor_menus`: name(_pa), description(_pa), cuisine, diet tags, price_from, price_unit, min_guests, `sections` (jsonb: titled sections of dishes).
- `vendor_links`: a venue and a vendor, kind (approved caterer / worked with), confirmed by each side; shown only when both confirm.
- `vendor_unavailable_days`: day, part (all day / morning / evening), status (booked / held). Public, no client details.
- `vendor_members`: a user's role on a vendor account (owner / staff).
- `vendor_leads`: sign-ups and claims from `/for-vendors` (insert only; founders read them).
- `vendor_activity_daily`: anonymous daily counts per vendor and kind (view, call, text, whatsapp, directions, share, instagram, website).

**People and planning:**

- `profiles`: id (the auth user), full_name, city, phone (E.164), adult_confirmed_at. The email lives in Auth only.
- `saved_vendors`: user, vendor, event (null = "Not sure yet").
- `inquiries`: user, vendor, event_slugs, event_date, start_time, guest_band, location, message, preferred_contact, language, details (venue / caterer / tour answers), sender name / phone / email, channel, status (sent / queued / failed…), failure, sent_at, **reply_answer** (the family's follow-up answer, the only column the app can write).
- `weddings`: title, wedding_date, planning_for, **traditions**, created_by.
- `wedding_members`: wedding, user, role (owner / planner / viewer; #104 renames them to owner / editor / suggester).
- `wedding_events`: wedding, event, event_date, guest_band.
- `wedding_bookings`: wedding, event, category, vendor (optional), note, updated_by.
- `wedding_invites`: token (32 hex), role, expires_at (14 days), uses / max_uses (20), revoked_at.
- `wedding_reactions`: wedding, vendor, user, reaction (love / maybe / no).

**Chat:**

- `conversations`: one per family and vendor; family_name ("Harjit K."), last_message_at, read and notified times for each side.
- `messages`: conversation, sender, sender_role, kind (text / photo / quote / menu / booking), body, data (jsonb: quote amount and unit, menu id), inquiry. Private bucket `chat-media`. Realtime on both tables.

**Reels** (data merged in #110; screens are in open PRs):

- `reels`: author, vendor (when posted as a business), video_path, thumb_path, duration_s, width, height, caption, event, status.
- `reel_vendor_tags` (pending / approved / declined by the vendor), `follows` (a person or a vendor), `reel_likes`, `reel_comments` (with hidden), `user_blocks`, `reel_reports`. Public bucket `reels`.

**Main server functions:** `search_vendors` (distance, category, text and fuzzy match, travelers, guests, max price, language, availability, sort), `create_inquiry`, `inquiry_emails_left_today`, `create_wedding`, `create_wedding_invite`, `wedding_invite_preview`, `accept_wedding_invite`, `wedding_members_list`, `remove_wedding_member`, `set_wedding_member_role`, `react_to_vendor`, `wedding_shortlist`, `start_conversation`, `send_message`, `mark_conversation_read`, `my_conversations`, `claim_chat_notifications`, `track_vendor_activity`, `vendor_public_stats`, `vendor_scorecard`, `vendor_date_status`, `touch_vendor_calendar`, and the reels functions (`reels_feed`, `create_reel`, `add_reel_comment`, `hide_reel_comment`, `decide_reel_tag`, `pending_reel_tags`, `report_reel_content`, `reel_person`, `reel_comments_list`).

**Sample data:** 149 sample vendors (7 or 8 in the common types, 2 to 4 in most others, including halal, Pakistani and Arab vendors), 5 with founding numbers, sample menus, links and a sample hall (Royal Orchard Banquet Hall) with approved caterers.

## 9. How to run it locally (Mac)

```bash
# One-time
brew install colima docker supabase/tap/supabase
colima start --cpu 4 --memory 6 --disk 40      # Docker engine; again after each restart
npm install

# Database (local Supabase in Docker)
npm run db:start        # first run downloads a few GB
npm run db:status       # prints the local URL and publishable key
cp .env.example .env.local
#   EXPO_PUBLIC_SUPABASE_URL=http://<your Mac's Wi-Fi IP>:54321   (ipconfig getifaddr en0; a phone can't reach 127.0.0.1)
#   EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY=<from db:status>
#   EXPO_PUBLIC_SITE_URL=                                          (empty until there's a domain)
npm run db:reset        # rebuild from migrations + 149 sample vendors
npm run photos:samples  # placeholder photos for the sample vendors

# App
npx expo start          # scan the QR code with Expo Go on the phone (same Wi-Fi)
```

- Supabase Studio: http://127.0.0.1:54323. Emails (sign-in codes, inquiry emails): Mailpit at http://127.0.0.1:54324.
- Local test phone sign-in: 15305550100 with code 123456.
- Checks before a PR: `npm run lint -- --max-warnings 0`, `npm run format:check`, `npm run typecheck`, `npm test`, `npx expo export --platform web`; after database changes `npm run db:reset && npm run db:test && npm run db:types`.
- Founder tools: `npm run vendors:import`, `photos:upload`, `vendors:invite`, `availability`, `report`, `i18n:review`, `demo:check` (see the README).
